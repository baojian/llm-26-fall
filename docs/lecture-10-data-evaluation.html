Lecture 10: Data preparation, evaluation, and experimental design

Week 10, November 11, 2026. This lecture connects the post-training workflow to the evidence needed to trust an improvement. The central question is: does the measured gain survive a controlled comparison on relevant held-out data?

1. Define the claim before building the pipeline

“Better data” needs a task, population, budget, and measurement. A useful question is whether removing exact duplicates improves held-out instruction following at a fixed training-token budget, while preserving performance on short factual answers. A change in aggregate score alone does not explain which population improved or which variable caused it.

Write an experiment record before running the final comparison: treatment, baseline, frozen model/tokenizer revision, data version, split unit, training budget, development-selection rule, evaluation protocol, and the smallest effect that would matter. Keep evaluation data out of every earlier fitting or selection stage.

2. A traceable data pipeline

Stage Output to preserve Example failure
Acquisition Source, version, access conditions, source ID Unknown provenance
Extraction Text plus parent-document ID Menus replace article content
Filtering Decision and reason Useful short answers rejected
Matching Exact keys or approximate match evidence False duplicate merges
Splitting Family/group assignment Related examples cross the split
Tokenization and packing Frozen tokenizer, boundaries, masks Prompt tokens scored as response targets
Sampling Source weights and exposure counts A small source repeated excessively

Preserve source identifiers through chunking and augmentation. Several chunks from the same document are not independent examples. A license or access record is separate from an estimate of content quality. A filter score also does not prove that text is factually correct.

For SFT, inspect instruction/response alignment and the response-token mask. For preferences, retain pair provenance, the rubric, and correlated candidate groups. For reward optimization, separate policy-training prompts, reward-model training pairs, and evaluation prompts. All three can become leakage routes.

Taught stage Fitting data Boundary to audit
SFT, Lecture 08 Demonstrations and response masks Evaluation answers or related source documents in demonstrations
Reward model, Lecture 08 Preference pairs and rubric Evaluation prompt families in reward-model fitting or selection
PPO, Lecture 09 Prompts, sampled responses and rewards Evaluation tasks exposed during policy optimization

A prompt held out from PPO is not necessarily held out from SFT or reward-model training. Carry source-family IDs across stages and reserve final evaluation before model or prompt selection. The three training pools need not be mutually disjoint; the claim concerns their relationship to the evaluation population. When pretraining exposure cannot be audited, record that uncertainty.

Task definitions become data schemas

The instructor's 2025 benchmark lecture provides concrete preparation cases. Start by specifying what one example contains, what the target means, and which source identifiers must survive transformation.

Case Input and target Preparation check

These task distinctions come from GLUE, Section 3, STS, Section 2 and Table 1, and SuperGLUE, Sections 3.2–3.3. The STS source establishes the lower endpoint as 0; the earlier lecture and GLUE paper's 1–5 wording should not be used to reject valid zero scores.

Write a short annotation rubric with positive, negative and borderline examples. Pilot it with independent judgments, retain disagreements, and record how they were resolved. Store the rubric revision alongside labels. For Week 8 preference pairs, also preserve candidate order, ties and annotator agreement: a grammatical sentence is not automatically the preferred response under a helpfulness rubric. These are recommended course data practices, not a claim that each historical dataset used the same annotation procedure.

3. Extraction and filtering

Extraction choices decide what becomes training text. Compare raw source, extracted text, and the downstream example on a small audited sample. Look for navigation, repeated footers, missing equations, broken lists, and lost speaker roles. Preserve enough information to reproduce a decision.

Quality is conditional on use. A rule rejecting all short documents could remove exact answers and concise code snippets. A language classifier can make errors on mixed-language text. Inspect both retained and rejected examples, including examples near the threshold. Report rejection rates by source or slice, rather than only a global retained-token count.

Primary examples: FineWeb, Dolma, and DataComp-LM. Their large published experiments are methodological references, not the required course compute budget.

Distractor construction is a quality decision

SWAG builds continuation choices using generated negatives and adversarial filtering; HellaSwag revisits the remaining shortcuts. Read the construction method in SWAG, Section 2 and the ablation in HellaSwag, Section 3.2 and Figure 4.

For a course dataset, retain candidate provenance, use a development audit to identify easy stylistic cues, then have people check that the intended answer is supported and alternatives are unsuitable. A difficult distractor can instead be another valid answer. Inspect length, formatting and answer-position cues; try an answer-only baseline. Strong performance without the required context is evidence to investigate a shortcut. Low performance does not certify that all shortcuts are absent. Freeze the final evaluation after construction choices.

4. Exact and approximate duplicates

An exact key is only as meaningful as its normalization rule. Unicode NFC, line-ending normalization, and trimming outer whitespace can remove superficial differences. Lowercasing, punctuation removal, or aggressive whitespace changes can collapse examples whose distinctions matter. State the rule explicitly.

For sets of word shingles AAA and BBB, Jaccard similarity is

J(A,B)=∣A∩B∣∣A∪B∣.J(A,B)=\frac{|A\cap B|}{|A\cup B|}.J(A,B)=∣A∪B∣∣A∩B∣​.

Thus MinHash collisions estimate that similarity. A finite signature is an estimate, and a match proposed by locality-sensitive hashing still needs the declared verification rule.

5. Split by the unit that can leak

Choose a grouping unit appropriate to the claim: source document, prompt family, author, repository, patient, time period, or interaction environment. For preference data, all pairs derived from one prompt should remain together. For chunked documents, keep parent and related-family IDs available.

Establish split membership before generating dependent pairs, chunks, or augmentations. Audit exact and approximate overlaps across splits. When grouping must change, preserve the mapping and reasons. A random row split does not make rows independent, and exact deduplication does not rule out semantic overlap or prior pretraining exposure.

Development data selects thresholds, prompts, hyperparameters, and stopping points. A final test is used after these choices are fixed. Repeatedly trying options on the final test turns it into development data, even if no gradients were computed on its text.

The scoring unit can also differ from the row unit. MultiRC reports answer-option F1 and exact match of each question's entire answer set. Four correct options out of five do not imply a correctly answered question. Keep the identifiers needed for both aggregation and group-aware uncertainty. SuperGLUE, Table 3.

6. Match exposure and compute

Removing records changes corpus size. Equal epochs then give different training-token counts. A data-policy study should freeze the model, tokenizer, optimizer, and processed-token budget, while reporting both retained tokens and actual processed tokens.

Keep total GPU-hours across all devices and runs, or CPU time for CPU studies. Record model and dataset sizes separately from runtime. An external resource has a source and cost; it is not an allocation from the course pool.

7. A benchmark is a complete protocol

The measurement includes dataset revision, task interface, prompt/template, decoding budget, answer extraction, grader, aggregation, and uncertainty. A familiar benchmark name does not pin all of these. Changing the number of attempts or giving tools changes the evaluated system.

Evaluation family Example measurement Limitation to inspect
Language modeling Token loss, PPL, BPB Tokenizer and context conventions
Classification or candidate scoring Accuracy, macro-F1 Label mapping, imbalance, candidate normalization
Generated answers Exact match, rubric, checked tests Equivalent answers, weak graders
Preferences Paired win rate Ties, length/style bias, judge identity
Code or interaction Tests passed, tasks completed, budget Environment, retries, hidden feedback

GLUE, SuperGLUE, and HANS remain useful teaching cases for task construction and shortcut analysis. Modern benchmark examples are useful for studying versioning, graded reasoning, tools, and interaction. They are not a substitute for evaluation matched to a project's question.

Controlled examples reveal what a dataset measures

LAMBADA selected passages through full-context and limited-context prediction checks. Its 10,022 filtered passages form development and test sets; its separate training text comes from different novels and is not filtered in the same way. Paperno et al., Sections 3.1–3.2. For a new context-use study, retain book/document IDs, document the context window, and compare both conditions on the same items. Correct prediction of a target word spanning several BPE tokens requires scoring the complete word.

BLiMP uses grammar-generated minimal pairs and checks which sentence receives higher probability. Warstadt et al., Sections 2–3. An authored example is “The keys beside the folder are missing” versus “The keys beside the folder is missing.” Preserve pair and template IDs, verify the intended contrast, and check for lexical cues. Template-based generation can create many related rows; a new-template generalization claim needs a corresponding split. Do not equate grammatical acceptability with a Week 8 human-preference label.

Dynabench studies data collection with people challenging a model and validating examples across rounds. Kiela et al., Sections 2–3. For a course adaptation, record the model, collection round, rubric and validation status. Use discovered failures for development, preserve a separate final check, and report performance by fixed evaluation round. Changing the test distribution while changing the model prevents attributing the score difference to the model alone. These design recommendations do not assume the historical web service is currently available.

8. Likelihood and generation answer different questions

Token perplexity is exp⁡(H)\exp(H)exp(H) for mean negative log likelihood HHH in nats per scored token. It is not directly comparable across tokenizers without controlling the scoring unit and conventions. Bits per byte uses total negative log likelihood divided by log⁡2\log 2log2 and the original UTF-8 byte count.

For multiple-choice evaluation, sum response-token log probabilities under each candidate, with the same context and boundary convention. Length-normalized scores can rank candidates differently. State the choice rather than treating normalization as an innocuous implementation detail.

9. Paired comparisons and uncertainty

Evaluate A and B on the same items and retain their paired outcomes. In a synthetic set of 100 independent items, suppose 50 are correct for both, 10 only for A, 14 only for B, and 26 for neither. The accuracy difference is (14−10)/100=4(14-10)/100=4(14−10)/100=4 percentage points.

A paired bootstrap resamples item indices and carries both systems' outcomes together. Compute the difference for each resample, then a declared interval. For the supplied fixture and seed, the central 95% percentile interval is approximately -5 to +13 percentage points. It crosses zero: the observed sample does not establish a reliable positive gain. This does not prove the systems are equivalent.

The interval conditions on the fitted systems, prompts, and grader. It omits training-seed variation, prompt selection, label error, and domain shift. Related observations need resampling at the relevant group level. More rows from the same family may add less independent evidence than new families.

Reading: Dror et al. (2018), assumptions and test selection.

10. Validate the evaluator

Worked example: reward coverage

Suppose the task is to return the square of an input. The training reward only checks input 2. Both return 4 and return x * x receive full reward. An independent check at input 3 expects 9 and rejects the hard-coded candidate.

Candidate Reward case: input 2 Independent case: input 3
Hard-coded answer 4: pass 4: fail
Square function 4: pass 9: pass

The notebook executes this authored fixture. It demonstrates an incomplete verifier, not a trained-policy result. Even passing both tests does not prove general correctness. Once a check guides a repair or candidate selection, it is development evidence; retain a separate final evaluation for the claim. This revisits the post-training objectives covered across Lectures 8–10 and prepares the independent evaluation of Lecture 11's adaptation experiments. For an empirical study of optimizing a proxy, read Gao et al., Scaling Laws for Reward Model Overoptimization. Their reward-model experiments are distinct from this two-function illustration.

Audit disagreements and failure slices

An exact matcher can reject an equivalent answer. A unit-test suite can miss incorrect behavior. An LLM judge can change its decision when answer order or presentation changes. Human assessors can disagree about an ambiguous rubric. These are failure modes to investigate, not universal error rates.

Build a small checked set containing clear successes, clear failures, and borderline cases. Test order swaps for pairwise judgments and state how ties are counted. Record the judge model revision, prompt, rubric, and access to reference answers. Keep its training and selection history separate from the system being evaluated when possible.

Error analysis should produce a testable next question. “Long responses fail more often” could reflect task difficulty, truncation, or a scoring artifact. Inspect examples before changing the model. Choose the next experiment on development data, then use a fresh or preserved final evaluation for the claim.

11. A minimum useful experiment report

State the question, treatment, and baseline. Document data provenance and splits, actual training exposure, model/template revisions, and evaluator. Report per-item or per-group outcomes, relevant slices, uncertainty, and a few checked failures. Identify which choices were made before final evaluation.

A negative result can be informative when the implementation and comparison are sound. A large score increase with leakage or a changed attempt budget does not answer the intended question. Tie the conclusion to the tested population and budget instead of claiming general model superiority.

12. From task adaptation to agent evaluation

The slide timeline traces changes in the evaluated object: GPT-1's supervised task adaptation, GPT-2's zero-shot transfer, GPT-3's in-context demonstrations, Codex's executable tests, InstructGPT's human preference comparisons, GPT-4's capability/exam evaluation, and budgeted reasoning and tool-using systems. These are different protocols, not a single cross-generation score curve. Actual figures and source sections are in the historical reading map. Official documentation verified GPT-6/6.1 interfaces on November 11, 2026; the requested GPT-6.2 endpoint was not verified, so no result is invented.

The four core modern cases ask different questions:

Case Evaluated output Essential boundary
HLE / HLE-Diamond Closed-ended expert answer Question-set identity, answer extraction, calibration and tools
SWE-bench family Repository patch Exact task set, snapshot, issue/regression tests and harness
Terminal-Bench series Environment outcome or artifact Agent/verifier separation, hardware, timeout and release compatibility
Agents’ Last Exam Professional deliverable Task subset, full-pass versus partial-credit scoring, model and harness

The versioned benchmark guide distinguishes first releases, papers and later revisions. Terminal-Bench 4.0 illustrates why rerunning an agent, regrading stored artifacts and reusing a compatible result are different operations. Original HLE and HLE-Diamond use different question populations. A changed score can reflect a changed task or verifier even when the agent outputs are unchanged.

For agent comparisons, record model snapshot, harness commit, task IDs, VM or container image, tools and network policy, reasoning/output budget, attempts, timeouts, failure/retry policy, grader revision, per-task artifacts and total cost. Pair systems on the same task IDs and initial states. A report that changes both model and harness measures a system improvement unless additional controls separate their contributions.
